# OMP Minecraft 26.2 适配与 Vulkan 支持统一实施计划

日期：2026-11-03（Asia/Seoul）；进度更新：2026-11-04。状态：S0～S3 已验收并推送；S3 提交 52e0a331；S4 本地集成与 Windows native 测试包已通过，离线检查点 d4d1f50a 已提交推送并核对远端。用户明确暂不启动游戏，真实客户端矩阵保留MANUAL/PENDING。

## 1. 目标与交付边界

在同一实施计划、同一版本交付中，完成 Minecraft Java 26.2 正式版适配，并同时支持 Fabric、NeoForge 上的原版 OpenGL 和实验 Vulkan 后端。不得把 Vulkan 或任一加载器留给下一次版本适配；下列阶段是同一交付的顺序检查点，不是拆分需求。

保留现有 Figura/Lua、YSM/Molang、模型库、衣柜、HUD、头像、预览、纹理与粒子、网络及 JNI 功能。以现有受支持行为为基准，不借迁移添加功能或重构无关系统。采用原版 Blaze3D 提供的 GPU 抽象，不新增独立 Vulkan 渲染器、VulkanMod 依赖或第二套 GPU 生命周期管理。Forge、Quilt 不在本次新增支持范围；既有原生平台产物的打包契约须保持，不据此宣称这些平台 Vulkan 已实测。

“支持完成”须有相应加载器和实际后端的行为证据。编译成功、选择了 Vulkan、后台自动回退到 OpenGL、CPU 路径回退均不能单独证明 Vulkan GPU 加速通过。

## 4. 源码差异对应的改动清单

### 4.1 版本、加载器与资源

- 涉及 `gradle.properties`、根和各平台 `build.gradle`、`settings.gradle`、Gradle wrapper，以及平台模组描述文件；按实际需要最小修改。
- Fabric 当前 Minecraft 约束为 `>=${minecraft_version}`，应使声明范围与本次实际验证的 26.2 范围一致，避免声明未经验证的未来大版本。
- NeoForge 当前上界为 `26.1.3`，必须更新到与选定 26.2 加载器兼容的明确范围；同步核对 Java、加载器、Mixin、AT、AW 和资源元数据。
- 对照原版资源包格式与着色器结构检查现有资源，仅变更确有格式变化的文件。保留语言、模型资源、许可证与嵌套依赖。

### 4.2 Minecraft API、Mixin 与提交渲染

- 核查 `common/src/main/java/org/figuramc/figura/mixin/render/`、`top/aihmc/omnimorph/mixin/` 和两平台入口；以精确方法描述符核对注入点、字段、局部变量与调用顺序，不通过调低 require 或吞异常掩盖失败。
- 26.2 `GpuDevice` 为封装后端的类；纹理格式使用 `GpuFormat`；`RenderPass.setVertexBuffer` 使用 `GpuBufferSlice`，`drawIndexed` 采用五参数接口。逐个迁移现有适配器、绘制路径和相关测试桩。
- 管线采用 `BindGroupLayout`，同时核查 shader uniform/sampler 声明、附件格式、深度、混合及索引类型；优先使用实际缓存与原版示例，而非旧签名兼容补丁。
- 26.2 PIP 无参构造，`prepare` 增加 `FeatureRenderDispatcher`，`renderToTexture` 增加 `SubmitNodeCollector`，旧 `bufferSource` 字段移除。迁移 `FiguraGuiRenderer`、`FiguraPortraitRenderer`、`LibraryFiguraPreviewRenderer` 及两平台注册；保留预览隔离、透明度、深度和 HUD 行为。
- 核查 Screen 访问迁移到 `Minecraft.gui`，以及字体准备/提交、输入、实体 render state 和粒子 API。根据完整调用链确认变化；不以 AST 猜测重命名作为最终事实。

### 4.3 Vulkan 与 GPU 加速

- 首要风险是 `render/acceleration/GpuStorageSupport.java`：当前直接查询 `GL.getCapabilities`，强制 `GlBuffer` 并以 `glBindBufferRange` 绑定存储块。相关 `GlBufferAccessor` 和 Mixin 配置也须核查。
- 优先让 `MinecraftGpuDeviceAdapter`、`GpuShaderProgram`、GPU arena/批提交复用原版的设备、缓冲、布局、管线与命令编码接口；读取原版 `DeviceInfo` 的能力及限制，避免在 Vulkan 下访问 GL 上下文。
- 已读取的 26.2 `RenderPass` 公共入口仅提供纹理与 uniform 设置，不能未经证实便声称存在通用 SSBO 绑定接口。S3 首先核实原版可表达的数据通道：优先使用受支持的缓冲/绑定布局，必要时比较沿用既有 uniform 分批路径的容量、绘制开销及行为。
- 已核实 `UniformType` 包含 `UNIFORM_BUFFER` 与 `TEXEL_BUFFER`，`BindGroupLayout.Builder.withUniform(name, type, GpuFormat)` 支持指定 texel buffer 格式。S3 优先调查 texel buffer 能否表达现有 pose/remap/model 数据及着色器读取，再与 uniform 分批方案比较；目前仅确认 API 存在，尚未验证可用于本项目全部加速契约。
- Vulkan 的 GPU 绘制和既有 Figura/YSM 加速路径均须验证；不把禁用加速、空绘制或总是回退 CPU 当作实现完成。若原版抽象无法保留必须的存储块能力，记录证据、受影响文件和可行方案，按范围控制请用户决定，不擅自实现独立 Vulkan 后端或降低验收标准。
- 对齐、容量、上传、索引偏移、资源回收、帧间同步和重载须按原版契约迁移。现有 CPU/JNI 故障回退保留；回退只证明恢复能力，不证明相应 GPU 路径通过。
- 着色器须同时通过 OpenGL 和 Vulkan 的原版编译链；检查显式绑定、顶点布局、矩阵、深度范围、UV/截图方向和预乘透明度，不根据 OpenGL 外观推断 Vulkan 正确。

### 4.4 纹理、截图和遗留 GL

- `HostAPI.screenshot` 当前异步读回后返回纹理；核查 26.2 完成回调、缓冲映射及纹理发布时序，验证得到的实际内容。仅在确有失败证据或 API 迁移必需时修复。
- 检查 PIP 的 output override、纹理 view/sampler 生命周期、窗口缩放和资源重载，保证状态恢复与异常路径安全，避免跨后端资源使用。
- `UIHelper` 的旧 FBO 调用在注释块内，`StencilHelper` 也为注释实现；`CustomFramebuffer` 含 GL 代码但不能仅凭存在便认定正式路径触发。S2 记录真实调用点，未调用遗留代码不作无关改造。

## 7. 已知阻塞与风险处理

1. NeoForge 官方 [#3230](https://github.com/neoforged/NeoForge/issues/3230) 的早期加载窗口/Vulkan 问题仅明确标记 26.3 修复，尚无本次 26.2 候选已回移的证据。先核对发行与源码，获准后用无 OMP 的干净客户端隔离。不得擅改用户 `fml.toml`；`earlyWindowControl=false` 只作为待确认的加载器临时方案，不能静默应用或当作默认全支持证据。

3. Vulkan SSBO 能力与现有 GL 加速约定存在接口差异。须完成 S3 数据通道论证；不把“GL 不再报错”视为 GPU 加速完成。
4. 可选第三方模组的后端支持独立核查；不承诺 Iris/VulkanMod 等未验证组合，不取消现有冲突约束。
5. 当前真实客户端未获启动许可、未执行验证；自动检查与研究结论只证明各自覆盖范围。无硬件或授权时保留明确证据缺口。
