# YSM 原生渲染引擎当前实现进度分析

> 评估基线：当前 Figura 工作区源码、`refs/Sparkle-Morpher` 参考实现，以及 `Plans` 下四个阶段计划书。
>
> 评估原则：计划书描述目标，源码决定当前状态。本报告只把已经能够从源码、调用链或测试中确认的能力计入“已实现”；仅有资源字段、解析入口或参考代码的能力，单独标记为“部分实现”或“未开始”。

## 1. 结论摘要

当前 YSM 原生引擎已经越过“只能读取模型”的阶段，形成了一个可运行的单机本地闭环：YSM 包能够被发现和读取，模型几何与贴图能够进入 `YsmModelRuntime`，第三人称主体和第一人称手臂已经接入 Figura 渲染 mixin，动画、controller、functions、动作和控件也已经进入运行时装配。

但当前实现还不能判定为 Sparkle-Morpher 的完整等价实现。最大的差距不是缺少某一个模型文件，而是通用运行时语义仍不完整：

1. 动画播放器是加权叠加模型，不是 Sparkle/Geckolib 风格的逐骨骼动画队列和完整过渡状态机。
2. controller、Molang binding、functions 已有 MVP 或部分覆盖，但 slot、transition、事件边界和查询变量覆盖面仍不足。
3. `YsmSubEntity` 已保存 projectile/vehicle 资源和动画字段，但当前子实体主要是静态渲染，没有独立的动画播放器、controller 和真实实体上下文。
4. 第二阶段的 Figura 后端 YSM 同步、第三阶段的 native/SIMD/GPU 加速、第四阶段的加密 `.ysm` 和公模库，在当前 Figura 主源码中都没有形成可确认的实现闭环。

因此，当前最准确的总体判断是：

> **第一大阶段的主体本地能力基本落地，但验收项仍有若干高风险缺口；4.1/functions、controller、action/control 属于部分落地；第二至第四大阶段尚未进入可交付实现阶段。**

不使用百分比描述进度，因为各阶段的目标粒度不同，且“类已存在”“资源已装配”“语义已对齐”不能等价换算成同一个百分比。

## 2. 评估口径与状态标签

为了避免把计划书中的目标误写成现状，本报告使用四种状态：

| 状态 | 含义 |
| --- | --- |
| 已落地 | 已有源码实现，并已进入主调用链或渲染链路；仍可能需要回归验证。 |
| 部分落地 | 主要路径存在，但语义覆盖、边界行为或目标验收仍不完整。 |
| 资源/入口 | 能发现、保存或转发资源，尚未证明对应运行时真正执行。 |
| 未开始 | 当前 Figura 主源码没有可确认实现；`refs` 中的参考代码不计入 Figura 已完成。 |

还需要区分四个层次：

- **存在代码**：类、字段或解析器存在。
- **进入主链**：资源从 loader/NBT 进入 `YsmModelRuntime`，并被每帧更新或渲染调用。
- **只有资源字段/入口**：资源被保存或有 hook，但没有独立执行逻辑。
- **语义对齐**：行为已经接近 Sparkle-Morpher，包括过渡、事件边界、slot 和 fallback 等复杂情况。

本次结论优先采用后两个层次，而不是只看类名。

## 3. 四个大阶段总体矩阵

| 阶段 | 计划目标 | 当前源码状态 | 判断 |
| --- | --- | --- | --- |
| 第一大阶段 | 单人、未加密 YSM 完整可用 | 包读取、几何、贴图、主体渲染、基础动画、controller、functions、action/control 已有主链 | **主体基本落地，尚未完成完整验收** |
| 4.1 / functions 与 Molang 对齐 | functions、事件、args/temp、controller slot、binding MVP | `YsmMolangFunctionRuntime`、`fn/args`、部分事件和绑定已存在 | **部分落地** |
| 第二大阶段 | 通过 Figura 中心后端同步模型运行时状态 | 普通 Figura HTTP/WebSocket 存在，未发现 YSM state/capability/full-state/delta 主链 | **未开始** |
| 第三大阶段 | 可回退的 native/SIMD/GPU 加速 | 当前 YSM 渲染仍为 Java `PoseStack` + `VertexConsumer`；加速类只在参考工程中可见 | **未开始** |
| 第四大阶段 | 加密 `.ysm`、公模库、管理和分发闭环 | 当前只有目录/zip 资源包逻辑，没有加密解包器或公模库模块 | **未开始** |

### 3.1 计划书与源码的版本差异

部分旧的子计划仍把 controller、animation、function 写成“尚未实现”。这与当前源码不完全一致：现在已经存在对应 parser/runtime，并且 `YsmModelRuntime.fromNbt()` 会注册 animation、controller、functions、actions 和 controls。因此这些内容不能继续按“完全没有实现”描述。

相反，不能因为类名已经出现，就把它们写成完整支持。例如：

- `YsmSubEntity` 保存 animation/controller JSON，不等于子实体拥有独立播放器。
- `YsmBinding` 注册大量变量，不等于所有变量都有真实实现；部分函数明确返回 `0`。
- `YsmControllerRuntime` 能执行 state/transition，不等于已经复制 Sparkle 的 slot registry 和 bone queue。
- `YsmPackage` 能打开 `.ysm` 后缀的 zip，不等于支持加密 `.ysm`。

## 4. 第一大阶段：当前已落地能力

### 4.1 YSM 包发现、资源读取和 NBT 装配

状态：**已落地，边界仍需回归**。

当前资源路径已经形成如下闭环：

```text
本地 Avatar 路径
	-> YsmAvatarDetector / LocalAvatarLoader
	-> YsmPackage
	-> YsmManifestReader / YsmResourceIndex
	-> YsmAvatarLoader
	-> Avatar NBT cache
	-> Avatar.loadAvatar
	-> YsmModelRuntime.fromNbt
```

已确认的能力：

- 支持目录形式的 YSM 包。
- `YsmPackage` 支持 zip 文件系统，并能识别根目录模型包或单层子目录模型包。
- manifest 支持新旧格式，并收集 model、arm、texture、animation、controller、function、sound、language、projectile、vehicle 等资源索引。
- `YsmAvatarLoader` 会把 main/arm 模型、贴图 entries、动画、controller、functions、actions schema 和 sub-entities 写入 Avatar NBT。
- `YsmModelRuntime.fromNbt()` 会重新解析这些资源，并注册到对应 runtime。
- 缺少可选资源通常不会阻断主模型加载。

当前限制：

- 没有加密包解密流程；`.ysm` 目前只能在其本身是可读 zip/目录结构时进入现有路径。
- 文件夹、zip、大小写路径和多层目录的扫描一致性缺少系统测试。
- 资源加载器、缓存和 runtime 的错误诊断虽已有日志，但还没有覆盖所有失败阶段的统一报告。

### 4.2 几何解析与主体渲染

状态：**已落地，渲染语义仍需回归**。

已确认：

- `YsmGeometryParser` 将 Bedrock/YSM 几何解析为 YSM 自己的骨骼、cube、quad 和 transform 数据。
- `YsmModelRuntime` 创建 part、attachment point、renderer、animation player、action runtime 和 functions runtime。
- `YsmRenderer` 使用 Java `PoseStack` 与 `VertexConsumer` 提交主体、附件、第一人称 arm 和静态 sub-entity。
- `LivingEntityRendererMixin` 在 YSM 主体生效时提交 YSM 模型并取消原版主体提交。
- 切换或关闭 runtime 时会释放 YSM 纹理和子实体资源。

这说明 YSM 已经不是经过 Figura 普通模型管线“伪装渲染”，而是有独立的原生几何和渲染分流。

尚未完全验收的部分：

- PartMask、Locator、背景/GUI 部件和附件 pass 的完整语义需要用多种模型回归。
- 透明贴图、复杂附件、武器挂点和第三人称手持物品的矩阵结果还没有被测试套件完整覆盖。
- 当前渲染器没有 native/GPU 后端，性能仍属于 Java CPU 路径。

### 4.3 贴图选择与衣柜入口

状态：**已落地**。

`AbstractAvatarWidget.addYsmTextureMenu()` 已对 YSM Avatar 增加贴图 ContextMenu：

- 从 manifest 读取可用贴图选项。
- 显示当前选择。
- 通过 `YsmTextureSelectionStore` 按模型路径持久化选择。
- 当前选中 Avatar 发生切换时重新加载本地 Avatar。

这已经是用户可见的 YSM 贴图选择闭环，不只是 loader 层支持多张贴图。

### 4.4 基础动画与 extra animation

状态：**部分落地，简单模型可工作，复杂语义未完全对齐**。

`YsmAnimationPlayer` 已具备：

- clip 注册和名称归一化。
- 基础状态动画和 native state。
- extra/action 动画播放、停止、权重、fade 和 loop/once 等基础模式。
- timeline、sound、particle 基础事件入口。
- `pre_parallel` / `parallel` 零 scale 默认隐藏骨骼识别。
- extra 动作通过非零 scale 恢复被基础隐藏的骨骼。

原有动画分析中“默认隐藏污染后续动作 scale”的问题已经按通用机制处理：基础隐藏状态与动作期间的临时 scale 被分开考虑，不依赖具体模型名或骨骼名。

仍未达到 Sparkle 等价的原因：

- 当前播放器主要是每帧重置 pose，再对 active animations 做加权位置/旋转叠加和 scale 叠加。
- Sparkle 的 `AnimationControllerInstance` 以 controller/bone queue 为中心，拥有 beginning/ending transition、snapshot、剩余事件补发和 scale transition special。
- loop 边界、play-once 的尾部事件、ending transition 和多个 controller 同时影响同一骨骼的优先级仍需继续对齐。

因此，“动画文件可以读并播放”已经成立，但“复杂动画语义完全一致”尚未成立。

### 4.5 Animation controller

状态：**部分落地，并已进入主链**。

当前已确认的能力：

- `YsmAnimationControllerParser` 解析 controller JSON。
- `YsmControllerRuntime` 支持 initial state、states、conditional animations、transitions、on_entry、on_exit、blend/context 等字段的运行时路径。
- `YsmModelRuntime.fromNbt()` 会创建 Molang engine，并注册 animation controllers。
- controller function animation 能由 `ctrl.set_animation` 等绑定函数触发。

主要缺口：

- 没有完整复制 Sparkle 的 player/projectile/vehicle controller slot registry。
- controller runtime 与 animation player 的过渡、loop mode、hold-on-last-frame 语义仍是简化实现。
- `pre_main/main/post_main`、`hold/use/swing`、`armor`、`vehicle`、`projectile` 等 slot 的统一绑定和执行时序仍需收束。
- controller context 中的动画时间、render layer、transition snapshot 等信息并未达到 Sparkle 覆盖面。

### 4.6 Functions、事件和 Molang

状态：**4.1 MVP，部分落地**。

当前 `YsmMolangFunctionRuntime` 已有以下基础：

- functions 列表加载。
- `fn.xxx` 风格的函数注册/调用路径。
- 事件与参数传递。
- `args` 当前参数读取。
- temp/controller scope 的运行时基础。
- 递归保护。
- controller slot 和未绑定事件的处理入口。

当前 `MolangBindings` 也已注册 `query/q`、`ctrl`、`ysm`、`fn`、`args` 等命名空间，并提供 `loop`、`for_each` 等基础函数。

但这仍不能写成“functions 完整支持”：

- slot 生命周期与 event 在 controller 更新前后的确切时序还需要固定并测试。
- 作用域隔离、错误调用栈和模型/文件级诊断还不够完整。
- `YsmBinding` 中有一批兼容占位项，例如 `dump_mods`、`dump_effects`、`dump_biome`、部分 curios/particle/bone 函数返回默认值。
- Sparkle 的 `YSMBinding`/`CtrlBinding` 还覆盖大量装备、武器、药水、实体、船、环境和 mod compat 查询，当前 Figura 只实现了其中一部分。

### 4.7 Action、control 和轮盘布局

状态：**基础功能已落地，完整 UI/语义仍需补齐**。

`YsmActionSchemaParser` 已能处理：

- `controls` / `control`。
- `actions` / `action`。
- `properties.extra_animation`。
- `extra_animation_classify` 数组和对象形式。
- `extra_animation_buttons`。
- 旧版 `ysm_extra_info.extra_animation_names`。
- toggle、slider、enum、color、text、number、keybind、button、label、separator 等控件类型。
- range、option、default value、binding、page 和 config form。

`YsmActionWheelLayoutStore` 已有 8 槽和按 model/action 保存布局的基础；`YsmActionRuntime` 已被 `YsmModelRuntime` 创建并用于动作注册、触发和状态查询。

需要注意的边界：

- 解析 schema 不等于所有控件都已经有完整交互、快捷键和持久化语义。
- Sparkle 的轮盘页面、分类、返回和网络动作协议不能原样迁移到 Figura。
- 当前 action/control 更接近 Figura 本地运行时适配，尚未形成第二阶段的远端同步状态。

### 4.8 第一人称、手持物品和附件

状态：**部分落地**。

已确认：

- `PlayerRendererMixin` 能取消原第一人称手臂提交，并使用 YSM arm 路径。
- `LivingEntityRendererMixin` 已接入第三人称主体、动画更新和附件提交。
- `ItemInHandRendererMixin` 保留原版 item animation 路径。
- projectile 的 arrow/trident 入口已经存在。

尚未完全对齐：

- 第一人称 arm、主副手、盾、弓、弩、三叉戟等复杂 transform 仍需逐类验证。
- 不能把“原版 item renderer 仍被调用”误写成“所有 YSM Locator 手持物品语义已完成”。
- attachment point 和 item renderer 之间的矩阵、pass、透明度及遮挡规则需要更多回归用例。

### 4.9 Projectile、vehicle 和 sub-entity

状态：**资源/入口存在，运行时动画部分缺失**。

当前 `YsmSubEntity` 能保存模型、贴图以及 animation/controller JSON；`YsmModelRuntime` 也会读取并创建 sub-entity，renderer 能提交静态 sub-entity。arrow/trident 已有静态替换入口。

这只能证明“子实体资源可以进入 runtime”，不能证明“子实体已经拥有 Sparkle 的独立动画系统”。当前缺口包括：

- sub-entity 没有独立的 `YsmAnimationPlayer`/`YsmControllerRuntime` 更新链。
- projectile 没有完整的实体状态 Molang context 和独立 controller pipeline。
- vehicle 没有完整 renderer hook、origin/move/ride 状态和 controller。
- 子实体的 attachment、生命周期、缓存释放和真实实体绑定还需要系统验证。

## 5. Sparkle-Morpher 对照结论

### 5.1 可直接借鉴的部分

Sparkle-Morpher 对当前 Figura 最有价值的参考是运行时语义，而不是类结构：

- controller slot 的分类和执行顺序。
- animation controller 的 state、transition、begin/end transition。
- 逐骨骼动画队列和 loop/event 边界处理。
- `ctrl.*`、`ysm.*` 查询变量的命名和常见模型依赖。
- projectile/vehicle 独立 bundle 与独立 controller。
- native 加速的 capability、backend decision 和 Java fallback 设计。

### 5.2 不能当作 Figura 已完成的部分

`refs/Sparkle-Morpher` 是参考工程，不是当前 Figura 的实现证明。特别是：

- Sparkle 的 Geckolib controller/queue 代码不能证明 Figura 已有相同语义。
- Sparkle 的 `YSMBinding`/`CtrlBinding` 覆盖范围不能证明 Figura 的 binding 已全部实现。
- Sparkle 的 native/Zstd/ABI 代码不能证明 Figura 已有加速库或 JNI。
- Sparkle 的 server/entity sync 不能作为 Figura 第二阶段的架构目标。

### 5.3 网络同步边界

第二大阶段计划已经明确：YSM 同步应沿用 Figura 的中心后端、HTTP Avatar 资产、WebSocket Event/Ping 和订阅关系，不能复制 Sparkle 依赖 Minecraft 服务端 Mod 的 `C2S/S2C` entity packet 模式。

当前源码中可以确认普通 Figura 网络能力存在，但没有确认以下 YSM 专用闭环：

- YSM capabilities 协商。
- model instance/full state。
- action event delta。
- public control delta。
- texture delta。
- sync variable store。
- sequence、TTL、乱序丢弃和远端 action runtime 应用。

因此第二大阶段不是“已经有同步，只差测试”，而是**架构边界已经写清楚，但 YSM state sync 尚未实现**。

## 6. 各阶段当前进度详表

### 6.1 第一大阶段：单人未加密 YSM

**判断：主体能力基本落地，完整验收未完成。**

已达到：

- 未加密目录和 zip 的识别、读取和缓存。
- 新旧 manifest 和主要资源索引。
- main/arm geometry、贴图和 Java 原生渲染。
- 第三人称主体替换和第一人称 arm 入口。
- 基础 native state、clip、extra action、timeline、sound/particle 入口。
- controller、functions、action/control 已进入 runtime 装配。
- YSM 贴图菜单和本地持久化选择。
- scanner、debug dump 和局部 smoke test 基础。

未达到完整验收：

- complex transition/bone queue。
- 全量 controller slot 和 binding。
- first-person/item/attachment 全组合。
- projectile/vehicle 独立动画。
- 目录/zip/多模型/异常资源回归测试。
- 所有计划书中列出的模型样例都经过可重复实机验证。

### 6.2 4.1：Functions/Molang MVP

**判断：核心 runtime 已有，完整语义和诊断未完成。**

当前已经超过“只解析文件名”的状态，能够加载 function、调用 event、传入 args，并接入 controller/Molang；但 slot 时序、作用域、错误报告、绑定覆盖和模型兼容性仍是后续重点。

### 6.3 第二大阶段：Figura 后端同步

**判断：未开始。**

当前普通 Avatar 的 HTTP/WebSocket 基础设施不能直接计入 YSM 同步完成。需要新增并验证 YSM 专用的 state 消息、能力协商、动作事件、公共控件、贴图选择和远端 runtime 应用，同时保持普通 Figura Avatar 兼容。

### 6.4 第三大阶段：Native/SIMD/GPU

**判断：未开始。**

当前 `YsmRenderer` 仍然是 Java CPU 路径，未发现 Figura 主源码中的 acceleration loader、ABI bridge、GPU mesh、SIMD validator 或 backend decision。Sparkle 的加速实现只能作为后续设计参考。

### 6.5 第四大阶段：加密模型与公模库

**判断：未开始。**

当前 `YsmPackage` 的 `.ysm` 后缀判断只负责尝试打开 zip 文件系统；没有 YSMParser 等价的 crypto detector/decryptor、Java 多版本解密、加密缓存、公模库 HTTP API、SQLite metadata、管理员鉴权或公模管理 UI。

## 7. 主要风险与证据不足

### 7.1 最大风险：把“解析成功”当成“运行时对齐”

当前已经有较多 parser 和字段，容易产生“功能已经完成”的错觉。真正容易暴露差异的场景是：多个 controller 同时作用于同一骨骼、transition 中触发 event、extra 动作临时显示隐藏附件、第一人称同时处理 item 和 arm、projectile/vehicle 有自己的动画上下文。

### 7.2 绑定占位值会造成静默错误

当前 `YsmBinding` 对一部分能力提供了真实查询，对另一部分能力使用零值或空操作 fallback。这样模型通常不会崩溃，但条件动画可能永远不触发，表现为“模型能加载但动作不对”。Scanner 应把 unsupported binding 和明确的 zero fallback 区分展示。

### 7.3 子实体字段容易被误判

`YsmSubEntity` 中存在 animation/controller 数据，只说明 loader 没有丢弃资源；由于当前渲染主要是静态 sub-entity，不能把这些字段计入“projectile/vehicle 动画已完成”。

### 7.4 缺少主链级测试

`YsmPhase41SmokeTest` 已覆盖局部函数、slot、binding、role、controller parser 和 control parser，但尚未覆盖从包读取到 NBT、runtime 创建、每帧动画更新、渲染分流和资源释放的完整链路。当前没有编译或测试执行结果，因此本报告不把 smoke test 的存在写成整体通过。

### 7.5 计划书验收样例尚未形成自动化矩阵

计划中列出的模型样例可以作为回归集，但目前缺少统一的：

- 资源扫描结果快照。
- controller/function 编译结果快照。
- unsupported binding 报告。
- action/control schema 快照。
- render path 和 runtime lifecycle 结果。

## 10. 最终判断

当前 Figura YSM 原生引擎已经具备可运行的未加密单机基础：资源能进入 runtime，主体能被原生渲染，动画/action/controller/functions/control 也确实被装配并执行。这是第一阶段的实质性进展。

目前还不应宣称“YSM 原生引擎已完成”或“已与 Sparkle-Morpher 完全对齐”。正确的工程状态是：**第一阶段主链已成形，运行时语义对齐仍在进行；4.1、controller、action/control 为部分完成；第二阶段同步、第三阶段加速、第四阶段加密与公模库尚未开始。**

后续工作应优先围绕通用 controller/animation/binding/sub-entity 机制补齐，而不是继续为单个模型增加名称或骨骼特例。只有当第一阶段的主链回归、复杂动画语义和子实体边界稳定后，才适合进入同步、加速和加密分发这些更高阶段的工作。
